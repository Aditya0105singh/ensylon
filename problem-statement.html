01Background

Modern cloud-hosted applications generate thousands of signals every minute — metric anomalies, application error logs and monitoring alerts. When something goes wrong, these signals arrive in a flood.

The same underlying problem can simultaneously trigger a metric spike, a burst of application error logs and a downstream latency alert. An on-call engineer currently sees dozens of separate signals and must work out by hand that they describe one incident, not many.

Ensylon is building an AIOps layer that groups correlated signals into a single actionable incident, scores it by impact and confidence, and drafts a structured incident ticket for human review and approval before it is raised.

Your challenge is to build a working prototype of this system in 24 hours.

02Problem Statement

Given a continuous stream of raw signals from three monitoring sources, build a system that:

  1. Ingests and parses raw signals from each source format
  2. Redacts PII — strips or replaces all personal information before any further processing or storage
  3. Normalises each signal into a common canonical schema
  4. Detects anomalies within each normalised signal
  5. Correlates anomalous signals into candidate incident clusters using multi-dimensional evidence
  6. Validates candidate clusters before accepting them as real incidents
  7. Scores each accepted incident by impact severity and correlation confidence
  8. Drafts a structured incident ticket using the Claude API and submits it for human review — a ticket must not be published without explicit human approval

The core principle

Time proximity alone does not prove correlation.

Two signals that arrive close together belong in the same incident only if there is structural evidence — a shared service path, a topology dependency, similar log templates, or a combination — supporting that grouping.

03Signal Sources

The simulator emits raw signals from three sources, each in its own native format and on its own stream (see Section 5). Your ingestion layer must handle all three.

3.1 CloudWatch Metrics

Alarm state-change payloads in AWS CloudWatch Alarm format, one alarm per event. Fields include alarm name and description, state change time, region, new and previous state, the trigger (metric, namespace, dimensions, statistic, period, evaluation periods, threshold and observed value) and the affected resources. The alarm description and the affected-resources block contain internal account identifiers and service-account emails that must be redacted.

3.2 Application Logs

Raw log lines as plain text, one line per event: ISO-8601 timestamp, level (ERROR, WARN, INFO), service, component, a context block in square brackets, and a free-text message. The context block holds key:value pairs — user: (customer email), ip:, session:, acc: (account number) and host: (internal hostname — sensitive, but not PII). Messages may repeat PII from the context and occasionally include customer names or phone numbers. All PII must be redacted before the signal is processed further.

04Canonical Signal Schema

After parsing and PII redaction, every signal — regardless of source — must be normalised into this schema before it enters the detection and correlation stages.

canonical signal
{
  "signal_id":      "uuid-v4 (generated by your system)",
  "timestamp":      "2026-09-26T10:01:03Z",
  "source":         "cloudwatch_metrics | application_logs | grafana_alerts",
  "environment":    "prod | staging | dev",
  "region":         "ap-south-1 | us-east-1",
  "service":        "payments-service | enrollment-service | carrier-service | ...",
  "component":      "db-connection-pool | api-handler | queue-processor | ...",
  "signal_type":    "metric_anomaly | error_log_burst | grafana_alert",
  "anomaly_score":  0.0,
  "evidence":       "[REDACTED] connection pool exhausted — template#118",
  "metadata":       {}
}
  • anomaly_score must be computed by your detection logic — it is not provided pre-computed.
  • evidence must contain no PII; redacted tokens must be clearly marked (for example [REDACTED]).
  • metadata is a free object for any source-specific fields your downstream stages find useful.

05The Signal Simulator

The simulator is hosted by Ensylon and runs for the whole event. It streams raw signals over HTTPS using Server-Sent Events (SSE), one stream per source. Connect with any SSE-capable client — or a plain HTTP GET that keeps the connection open — and process signals as they arrive.

StreamPayloadCopy
https://logs.nonprod.nexus.ensylon.com/sim/stream/aiops-logs Application logs · plain text
https://logs.nonprod.nexus.ensylon.com/sim/stream/aiops-grafana Grafana alerts · JSON
https://logs.nonprod.nexus.ensylon.com/sim/stream/aiops-cloudwatch CloudWatch alarms · JSON
  • The simulator injects realistic, synthetic PII into the fields described in Section 3. None of it is real customer data, but your pipeline must treat it as if it were.
  • Every event has a sequence id. If your connection drops, reconnect with the Last-Event-ID header (standard SSE clients do this automatically) and the stream resumes from the next signal, so none are lost.
  • The stream sends a keep-alive comment (:keepalive) every 15 seconds. Signals arrive in bursts, and there will be stretches with no signals at all — your system must handle silence gracefully, without crashing or raising incidents from it.
connecting · SSE wire format
curl -N https://logs.nonprod.nexus.ensylon.com/sim/stream/aiops-logs

# SSE wire format (same on all three streams):
id: 000042
event: signal
data: <payload — plain text on aiops-logs, a JSON string on aiops-grafana and aiops-cloudwatch>

Your system must handle signals as they arrive — you may not use the simulator’s internals, its configuration or any other endpoint on its host. Treat the three streams as your only input.

07What You Must Build

Your system must implement the following five components end to end.

C1Ingestion, PII Redaction & Normalisation

Parse raw signals from each of the three source formats. Detect and redact PII — including but not limited to email addresses, IP addresses, session tokens, account numbers, personal names and internal service-account identifiers. Normalise each parsed and redacted signal into the canonical schema in Section 4.

C2Anomaly Detection

Compute an anomaly_score (0.0–1.0) for each normalised signal and flag signals above your chosen threshold as anomalous candidates for correlation. You may use statistical methods (z-score, EWMA), rule-based thresholds, log template frequency analysis (for example Drain3), or any combination. Document your approach.

C3Correlation Engine

Group anomalous signals into candidate incident clusters. Your correlation formula must use at least three of these dimensions:

DimensionDescription
Temporal (T)Time proximity of signals within a correlation window
Service (S)Shared or related service path
Topology (D)Hop distance in the service dependency graph
Evidence Similarity (E)Similarity of log templates or alert rule names
Component (C)Same infrastructure component

Define your correlation formula, dimension weights, correlation window and merge threshold explicitly. Signals that exceed the merge threshold are grouped together; signals that do not remain separate.

C4Incident Validation & Scoring

Before accepting a candidate cluster as a real incident, validate it. Apply at least two validation checks of your own design — for example an internal coherence check, an environment consistency check, or a bridge-signal check that prevents weak chains.

For each accepted incident, compute two scores separately — do not blend them:

  • Impact Severity (0–100) — based on blast radius, business criticality of affected services and anomaly magnitude
  • Correlation Confidence (0–1) — based on cluster density, topology support and evidence agreement

C5Ticket Drafting & Human Review

Use the Claude API credentials provided to draft a structured incident ticket for each accepted incident. The draft must include a title, impact severity, correlation confidence, affected services, a signal timeline with source labels, observed evidence (facts only, clearly distinguished from suspected root causes) and suggested investigation steps.

The draft must be presented to a human reviewer who can approve, edit-and-approve, or reject it. A ticket is written to output/tickets/ only after explicit human approval.
